# 变量审查：本次备注优先与执行反馈

## 原因与链路检查

备注原先可以完整通过UI、Actions快照、Workflow、Prompt构建和Streaming请求。输入框没有maxlength；上下文超出预算会明确拒绝，不会静默截掉备注。Actions在第一次异步等待前复制备注字符串，随后修改输入或配置不会改动当前请求。

问题出在任务组织和反馈：备注在大段业务数据后，仅被定义为“审查重点和检索线索”，没有先执行的明确优先级；默认策略更长且具体。最终协议也没有逐项检查回执，不能区分遗漏、证据不足和程序拒绝。

## 调整

- 核心规则确定：不可修改的系统安全规则 > 本次备注任务 > 默认/自定义全面审查策略。先处理备注，再完成原有四阶段及必需装备核验。
- 完整备注保留在user数据消息前部，独立于默认策略及正文事实。原文不进入system指令，不变成事实或绕过安全规则的授权。
- 本地按明确对象、现有字段和变量域建立稳定任务ID。服装任务覆盖已存在的衣着与装备记录；背包任务指向实际物品列表；只指定NPC时可覆盖该人物业务数据。未知人物、范围外业务或不能可靠定位的自然语言仍保留原文，不猜测成已完成。
- Streaming开始后直接展示冻结的玩家任务清单；只表示检查要求，不表示AI已完成。候选内容继续使用原有真实SSE，不用定时器伪造进度。
- 沿用说明/命令两标签协议，在说明中新增`备注检查`JSON行：taskId、checkedPaths、observations、conclusion、reason。无需第二轮AI请求。

## 反馈如何核对

完整响应后，将回执与冻结任务、实际业务范围及修改前快照比对。每个任务范围都必须出现在checkedPaths，且每个范围至少有一个可对应的真实字段观察；重复、无效、观察值不一致、部分覆盖或裁剪均不能显示完整检查已完成。回执格式损坏不会变成修改命令，而是反馈未完成。

“已检查”表示AI提交了与范围和快照相符的回执，并不表示程序独立证明模型已经完整理解所有语义。程序无法观察模型内部是否逐项认真阅读；界面明确这一限制。尤其是大型容器，字段观察只能核对数据来源，不能证明每条记录的语义判断都正确。

- 已检查，无需修改：回执范围/当前值匹配，没有相关候选命令、实际Diff或未解决疑点。
- 已检查，发现修改：回执匹配，且程序模拟产生了相关真实Diff。应用前标注尚未应用。
- 证据不足，未修改：回执可核对，但不能形成有效且有依据的修改。
- 命令被拒绝：关联命令被程序拒绝；展示真实拒绝原因，不显示已修复。
- 未完成检查：缺少可核对回执、无法定位、范围不全等。即使有部分相关Diff，也单独列出，不伪称完整任务已完成。

界面同时显示AI提出、程序接受、拒绝数量和相关变更数量，可展开核对范围。确认应用成功后才将模拟变更标为已应用。无备注不显示额外清单或反馈区。

## 安全和费用边界

备注默认只提供任务方向。无论是“检查是否穿袜”还是“已经穿上白袜”，实际修改仍须依据当前变量、正文、可信基准和业务规则。命令验证、Simulation、真实Diff、Fingerprint、Safe Apply、智能精简与装备资产守恒、取消和错误处理均沿用原流程。备注反馈不参与写入，也不会更改存档Schema。

没有新增独立AI调用；任务和回执使用同一次请求。新增结构化字段会占用少量输入/输出token，仍计入原动态预算，不声称费用绝对不变。

客户更新文案：变量审查会优先处理本次备注，并逐项展示检查反馈；可清楚区分无需修改、发现变更、证据不足、命令被拒绝和未完成检查，所有修改仍需预览确认后生效。
